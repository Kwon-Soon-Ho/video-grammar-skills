# 게시 절차 독립 검토

판정: **보완된 게시 절차의 정적 검토에서 미해결 차단 지적은 없다.** 최초 지적 2건은 코드 보완 후 재확인했다. 게시를 실행하지 않았으며, 지금 게시의 모든 선행조건이 충족됐다는 판정도 하지 않았다. 최종 PDF 합격·시범 완료·사람 승인은 이번 검토 대상이 아니다.

## 실제로 읽고 확인한 범위

- 게시 코드: 최초 1~96행, 보완본 1~103행 전문.
- 보고 정리 코드: 최초 1~93행, 보완본 1~95행 전문.
- 보완 전 코드 2개가 `보고서원본/보완이력/04_*_보완전.py`에 보존된 것을 확인했다.
- 기존 기획 PDF는 경로 목록만 확인했다. PDF 내용은 읽지 않았다. 실제 7개이며 루트 1개·backup 6개의 구분을 복사 계획이 유지한다.
- 실행 완료 기록은 당시 3단계 진행 중이라는 상태 확인에만 사용했다. 단계 완료를 재검수하지 않았다.
- 3단계 입력 연결목록 전문과 카드 첫 65줄은 JSON export의 상대 경로 문맥 확인에만 읽었다.
- 보완본 2개의 AST 문법 검사를 했다. 코드를 import하거나 실행하지 않았고 사본 실패시험도 하지 않았다.

## 최초 지적과 보완 재확인

### B01 - 새 파일 전용 생성

최초 보고 정리 7~9행은 부재 확인 뒤 write_text의 w 모드를 사용했다. 검사 뒤 같은 이름의 파일이 생기면 덮을 수 있었다. 보완본 9행은 `open('x')` 배타 생성을 사용한다. 게시 쪽은 기존 `xb`를 유지한다. 이미 있는 파일은 덮지 않고 중단하므로 정적 검토 범위에서 해소됐다.

### B02 - 전체 쓰기 목록과 완료 직전 검증

최초 코드는 복사 pairs 뒤에 생성하는 접수·안내 4개를 사전 충돌 검사와 해시 영수증에 넣지 않았고, 완료 직전 전체 원천·목적지 재대조가 없었다.

보완본 81~102행은 복사 목적지·생성 4개·완료 기록 2개를 첫 쓰기 전에 중복·부재 검사한다. 생성 문서도 고정 bytes와 SHA를 계산해 created 목록에 기록한다. 모든 복사 원천·목적지와 생성 문서를 마지막에 전체 대조하고 보호 pin을 확인한 뒤 완료 영수증을 쓴다. 두 완료 기록의 동일 bytes도 재읽는다. 정적 검토 범위에서 해소됐다.

현재 순서는 **선행 검토·검사 확인 → 전체 쓰기 계획 고정 → 복사·생성과 직후 검사 → 전체 원천·목적지·생성 문서 재대조 → 보호 pin → 완료 기록 2개 생성·재읽기**다. 완료 표시를 먼저 쓰지 않는다. 실패한 부분 사본이 남을 수는 있으나 완료로 표시하지 않으며, 결과·backup 폴더 존재 검사가 검토 없이 재실행하는 것을 막는다. OS 배타 잠금이나 여러 파일의 원자적 트랜잭션을 보장한다고 하지 않는다.

## 최종 PDF 단계로 남기는 확인과 선택 제안

- 보고 정리 25·69행의 9쪽·최종 10쪽은 하드코딩이다. 후속 최종 PDF 검토에서 실제 카드 위치·페이지수와 일치하는지 확인해야 한다. 이번 검토로 확인했다고 하지 않는다.
- 주요 안내 경로는 현재 백틱 문자열이다. 저장 위치에 맞는 Markdown 클릭 링크를 추가하면 파일을 찾기 쉽다. 두 위치에 같은 보관 문구를 복제하므로 경로 기준을 명시하면 좋다. 이는 정적 게시 절차의 차단 지적은 아니다.
- 조회용 JSON의 내부 상대 경로 해석 루트는 `Phase 00/backup/2026-10-16_소량사본시범/실행원문/실행/eval-03-적용성검토자/candidate/inputs/Phase00/`라고 보완본 76행에 명시됐다. JSON bytes를 고치거나 독립 실행 DB로 안내하지 않는다.
