## 초기 위험

1. **수정 범위 확장**: ‘기록 정리’ 지시를 핑계로 source, 영상 identity, 시간/PTS, 좌표, 수치, 분류 의미, 승인, 현행 정본을 함께 수정할 위험. 요청 파일·허용 JSON 경로를 먼저 고정하고 값 보존을 전후 대조해야 한다. 관측을 보완하는 값 추측도 금지한다.
2. **판본 위장**: schema_version만 0.2.0으로 바꾸거나 JSON hash를 영상 hash로 대입하여 구형을 이관할 위험. 구형은 원문/누락을 보존해 접수/준비 대기로 인계한다. 읽기 요청만으로 실제 접수를 실행하지 않는다.
3. **검사 결과 승인 전용**: valid/exit 0/빈 errors를 사실·공간 supported·사람 신원·회사·운영 승인으로 바꿀 위험. unresolved·사람 대기는 별도 보존하며 fact_verified/human_identity_verified/company_approved/operational_release의 false를 존중한다.
4. **backup·복구 선언만 존재**: 내용이 이미 바뀐 뒤 백업하거나 기존 backup을 덮고 ‘복구 가능’이라 보고할 위험. 입력 bytes/hash/경로를 변경 전에 고정하고 백업과 동일한지 확인한다. 복구는 해당 작업 이전 bytes로 제한하고 나중의 타인 변경을 덮지 않아야 한다.
5. **부분 쓰기 및 오류 은폐**: 검사 실패 후 draft/부수 파일을 계속 쓰거나 저장 실패를 성공으로 보고할 위험. 허용 산출물·임시파일·검사 출력을 포함해 전체 변경 목록을 확인하고 실패 시 중단/복구/남은 상태를 사실대로 보고한다.
6. **현재성 우회**: pin/hash 오류를 고치기 위해 manifest·정본·옛 receipt를 자동 갱신할 위험. 현재 검사 실패 시 사용 중단; 과거는 해당 판본/snapshot 범위의 읽기로만 설명한다. 새 문맥은 실제 근거로 별도 버전/문맥을 준비한다.
7. **경계 혼합**: R4 필드에 R5 새 기획 역할을 덮고, R6 CI 회신을 R7 품질 승인으로 복사하거나, R7 내용을 기존 규격에 강제 삽입할 위험. 별도 초안·질문/답변 문맥·별도 R7 참조와 판정/진행 상태를 분리한다.
8. **수행 평가 노출**: 수행 fixture에 기대 답·평가 문단·채점기/지표가 함께 들어가면 독립 성능 증거가 약해진다. 요청/근거 입력과 평가 설계/정답을 명시 분리하고 삭제·제외 목록과 원문 hash를 보존한다. 이번 개발 사례를 잠금/미사용 실평가라고 부르지 않는다. 새 평가설계 분리 사례는 R8-4의 필수 잔여다.
