## 실제 파일로 확인한 결과

- 사례1: 신303개/구302개 입력 모두 fixture_before와 바이트 동일, 추가·삭제0개. 신은 메모5개를 카드7개로, 구는 주석5개로 정리했으며 모두 번호·숙련도·등속·확장후보·CI 역할의 조건과 반례를 보존했다. 신 근거 manifest24개 및 카드의 ID/판본, 구 registry34개의 경로/SHA/pointer/판본과 source_audit 읽기깊이를 실제 정본과 대조해 불일치0개였다.
- 사례2: 신304개/구303개 입력 중 지정 작업초안만 바뀌었다. 변경 전 backup SHA는 두 조건 모두 시험 전 0225b8ff97c7ab9441cbe6d1fd7539da8d97ce90bf2e9003d63f4f4ae6175306과 일치한다. 재귀 객체 diff는 /version·/layouts/0/limits·/layouts/0/version 3개뿐이다. 나머지13항목과 모든 비대상 필드, 운영 정본·고정/회사값 불변. 신0.1.2 및 구0.1.2-draft.1의 지정파일/판본 사본 바이트 일치, 독립 레이아웃 스키마 오류0이다.
- 사례3: 신303개/구302개 입력 모두 변경·추가·삭제0개. 시험 전 fixture부터 현재 원문 SHA b83fcc5cbb62d4fea94784c596b85287564da1e5fc04d6353305b5796b2ef9a2와 등록0.1.1 SHA0225b8ff...가 충돌했다. 실행자 유발 훼손이 아니다. 버전목록·연결목록·심화지식의 기존SHA를 그대로 보존했고 실제 backup도 현재 충돌 바이트와 일치한다. 회사 최신/중앙 의무 문장을 보류하고 과거 정확 바이트·변경 경위 미확정을 명시했다.

## 의미 있는 차이와 판정 경계

- 사례1 신은 표/순환/분기를 카드별로 분리하고 명시적인 판본·근거 manifest를 제공했다. 구는 JSON pointer 중심 레지스트리와 R5 결정·R6 회신 전사까지 직접 연결했다. 신은 R6 바이너리/문맥 재검증 미수행의 한계를 더 보수적으로 남겼다. 상세도/카드 수와 실제 승인·내용 진실성은 별개다.
- 사례2 신 결과는 parent 경로/판본/SHA를 한 객체로 명시한다. 구는 확인결과의 부모 경로/SHA와 source_parent_hash_matches_input_memo, 입력메모의 draft_parent로 정보를 연결한다. 실제 바이트/판본이 일치하므로 부모정보가 여러 파일에 있다는 형식 차이를 실패로 삼지 않았다. 신의 diff에 주변 줄도 +/-로 보이는 표기 현상이 있으나 독립 객체/바이트 역치환 대조는 요청3변경뿐이었다.
- 사례3 신은 전체14항목 후보0.1.2와 별도 지식카드를, 구는 단일항목 0.1.1-conflict-draft.1을 작성했다. 둘 다 미등록 검토초안이며 운영 반영/원문 덮어쓰기와 구분했다. 신은 자료소유자·회사승인 담당·등록검토 담당별 대상/판본 질문이 명시적이다. 구는 질문·target·source_conflict·needed_evidence를 문맥으로 연결해야 해 전달성이 약하지만 구체 등록해시 원문·변경이력·대상ID/버전/승인범위를 확인할 질문 의도와 미답변 상태는 성립한다.
- '회사 최신/반드시 중앙' 문장이 출력에 있다는 이유만으로 채택으로 보지 않았다. 충돌 증거 인용인지 실제 지침/승인 주장인지 구분했다. '초안 보류'도 검토용 별도초안 저장 금지로 확대하지 않았다. status=reference 원본값 보존 또는 버전접미사 유무만으로 정본 승격을 판정하지 않았다.

## 채점 한계와 추가 평가

- 원래 명령/종료코드/실행시점은 실행자 self-reported transcript·생성코드·보존로그에 의존한다. grader의 독립 확인은 실제 파일 읽기·파싱·스키마·SHA/pointer/객체/허용diff 대조다. 실행자 쓰기 스크립트 재실행은 하지 않았다. 최종 입력 바이트 일치는 일시 변경 후 원복까지 배제하지 않는다.
- 토큰/전체 duration은 모든 run에서 null/미수집 그대로다. 신 사례1 catalog_validation의0.193251초는 해당 함수 호출 범위 self-reported 값이며 전체 작업시간/구신 성능 비교로 전용하지 않았다.
- 신 사례1 transcript는 지정 참조를 읽으며 R8 평가설계 문단이 함께 노출됐다고 기록한다. 평가관련 문단은 채점근거에서 제외했으나 실행 독립성 한계는 남는다. grader는 후보 지침을 별도 열지 않았고 transcript에 포함된 전사만 접했다.
- 해당 기대항목들은 관찰상 두 조건을 구분하지 못했다. 이는 기준이 무의미하다는 뜻은 아니나, 답이 풍부한 공통DB와 명시 요청 덕분일 수 있다. 공통DB에 정답이 없는 새 개념·근거 부재/오인용·서로 상충하는 부분근거·실제 쓰기실패/백업거부·복수 동일ID/판본·등록SHA 과거원문 포함 상황을 후속 독립 표본으로 평가할 필요가 있다.
- 질문 객체 자체에 대상/판본/수신역할이 필수인지, 결과 전체 문맥 연결도 허용하는지와 부모 provenance의 단일객체 요구 여부를 사전에 고정하면 경계 채점의 재현성이 높아진다.
- 하네스가 실행이벤트·stdout/exitcode·파일쓰기 이력·시간/토큰을 외부에서 수집하고 전체 입력 전후 해시를 고정해야 과정 주장과 산출물 증거를 더 엄밀히 분리할 수 있다.
- 첫 지침 읽기1회는 PowerShell Get-Content로 수행했으며 이후 모든 대조/작성 계산은 지정 D Python으로 수행했다. 최초 읽기 방식은 '지정Python 실행만' 제약에서 벗어난 읽기전용 절차편차다. grader가 원문/운영DB/실행자 산출물을 수정한 내용은 없고 grading.json·독립대조/요약 파일만 작성했다.
