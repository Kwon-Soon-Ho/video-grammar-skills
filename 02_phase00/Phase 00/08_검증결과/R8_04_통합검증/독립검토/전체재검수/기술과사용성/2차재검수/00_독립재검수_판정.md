## 새 R8 문맥 검사기: 독립 21조건

저자 v2 자체검사 결과는 **12조건·모델 시행0**으로 확인했다. 그 성적을 재인용하는 데 그치지 않고, v2의 정상사본을 이 폴더 `isolated/`에 새로 복제하여 독립 21조건을 실행했다. 원 v2 정상사본과 각 검사 입력은 호출 전후 불변이다.

정상1조건은 valid=true다. 아래 오류15조건은 모두 valid=false로 구조적으로 거부됐다.

- source 실파일 누락, basis 실파일 누락, source 참조키 누락, 빈 basis, source/basis 잘못된 SHA.
- receipt에 다른 R7 foundation 또는 다른 inventory SHA, 역사 foundation 변경 후 새 hash로 로컬 재고정.
- 중복 JSON 키, NaN 리터럴.
- 문맥 candidate_adopted/company_approved=true, 제한 소스 permission_granted=true, receipt 수행자의 full 사본 읽기 주장=true.

모든 변형과 재고정은 **새 C 반례 사본 안에서만** 했으며 운영 pin을 수정하지 않았다. 자기 코드의 hash와 후보 참조 집합을 묶는 것, 원래 R6/R7 manifest SHA를 상수로 유지하는 것, receipt의 source/copy foundation 및 inventory를 대조하는 것은 유효했다.

## 게시 전에 보완할 새 결함

### N01 — P2: 정정표 전체 records를 지우면 source/basis 검사가 사라짐

`R8_후보연결확인.py` 56~63행은 records를 순회하지만 최소 행수/필수ID를 확인하지 않는다. 정상 문맥에서 `현재상태_정정표.json`의 records를 `[]`로 만들고 해당 파일 SHA만 C 문맥에서 갱신하면 **valid=true**였다. 개별 행의 빈 basis는 거부하지만 모든 행 삭제는 통과한다. 이것은 새 문맥을 만드는 도중 정정 근거가 통째로 빠지는 경우를 검출하지 못한다.

**수정:** 현재 버전에서 요구하는 ST-R4/ST-R2/ST-R2-JSON/ST-HANDOFF/ST-R7-R8 ID 집합을 명시 검토하여 최소/중복/누락을 확인한다. 향후 정정 범위 변경은 새 문맥 버전/검토로 다룬다. 단순 행수만 검사하면 다른 행으로 대체할 수 있으므로 ID와 출처 역할을 함께 확인한다.

**재검사:** 전체 빈 목록, 필수1행삭제, 같은 행 중복/다른ID대체, 정상5행, 정상 source/basis 변경 감지를 확인한다. 내용을 자연어로 승인하는 기능으로 확대하지 않는다.

### N02 — P2: 정정표 자체의 회사/운영 승인 필드 모순을 거부하지 않음

정상 정정표의 top-level `company_approved=true` 또는 `operational_release=true`를 각각 넣고 그 파일 SHA만 C 문맥에서 갱신하면 모두 **valid=true**였다. 개별 row의 semantic_contract_changed는 false를 요구하지만 정정표 상위 권한 경계는 검사하지 않는다.

검사 결과 자신의 permission/company/adoption/release 값은 여전히 false다. 실제 회사 승인으로 승격된 것은 아니다. 다만 정정표의 모순된 선언까지 유효한 입력으로 받아들이므로 “정정은 승인 아님”이라는 계약의 구조 검사가 불완전하다.

**수정:** errata의 id/version/status 및 company_approved/operational_release=false를 현재 형식에 맞춰 명시 검사한다. 현재문맥·제한소스·receipt 각각의 승인 경계도 허용 필드/타입과 함께 검토한다. **재검사:** 두 승격값, 문자열 false/0 등의 타입 위장, 누락, 정상 false.

### N03 — P2: 조회 영수증 네 행의 고유 도구와 정수 종료코드를 확인하지 않음

68행은 길이4, valid is True, exit_code != 0만 확인한다. 정상 receipt의 첫 행을 4번 복제하거나 네 행의 exit_code를 Python/JSON boolean false로 바꾸고 C 문맥에서 receipt SHA만 갱신해도 모두 **valid=true**였다. `False == 0`이므로 bool을 성공 종료코드로 받아들인다.

**수정:** read_checks가 기대한 네 도구/범위 각각 한 번을 나타내는지와 `type(exit_code) is int and exit_code == 0`을 확인한다. receipt는 과거 선언의 참조 확인이고 이 helper가 네 검사를 live 실행하지 않는다는 표시는 유지한다. **재검사:** 행 하나중복/누락/미상도구, False/0.0/"0"/0 타입, 정상 네 고유도구.

### N04 — P3: 지수 오버플로 숫자는 엄격한 JSON 거부를 우회할 수 있음

read 함수22행은 NaN/Infinity 리터럴을 parse_constant로 거부한다. 그러나 정상 context에 미사용 숫자 메타데이터 `1e999`를 추가하면 표준 파서가 float infinity로 만들고 검사기는 **valid=true**를 반환했다. 사용되는 권한 필드/해시가 바뀌지는 않았다. 작은 local malformed-input 보조 검사에서 JSON1100중첩은 structured valid=false로 처리됐다.

**수정 권고:** parse_float 또는 전체 JSON 값 검사에서 math.isfinite를 확인하고, 파일크기/문서깊이·알 수 없는 상위 필드의 허용정책도 문서화한다. 이 현상만으로 네트워크/쓰기 위험이 생긴 것은 아니다.

## 게시 안전성과 범위 한계

- 검사기는 파일 읽기/JSON·SHA 비교만 하며 쓰기·외부 통신·프로세스 실행은 없다. 상대 경로를 base 안으로 resolve하여 상위/외부 읽기를 막고 실행 코드 SHA를 문맥에 묶는다.
- 현재 반환값은 R6_live_query/R7_live_query/behavior_or_content_verified/actual_video_analyzed/permission/company/adoption/release를 모두 false로 고정한다. 기존 구조조회 영수증을 모델 행동성적·권리허락·실영상 성능으로 과장하지 않는다.
- SHA는 보관된 bytes 동일성이다. 정정문의 진실성·권리·실제 명령 실행을 인증하지 않는다. 입력문맥/receipt/inventory를 모두 함께 교체하는 악의적 재작성의 전자서명·외부 신뢰 인증은 없다. 새 버전 문맥 게시에는 허용 변경·근거·receipt의 출처를 별도로 검토해야 한다.
- 후보파일 집합을 고정하므로 예상하지 않은 파일 추가도 멈춘다. 입력 전체의 원자적 snapshot/읽기잠금·완전한 TOCTOU 방지는 없으며 동시 변경 가능성은 별도 한계다. 파일/JSON 크기 제한도 현재 명시되어 있지 않다.
- 새 helper를 게시할 때는 지금의 C 도구/정상사본을 보존하고, 보완한 코드의 SHA·새 문맥·source/basis·receipt/inventory·기존 두 manifest를 **별도 새 R8 문맥**으로 명시 대조한다. 원 R6/R7 130pin이나 역사 receipt를 통과 목적으로 재생성하지 않는다.

## 같은 턴의 v3 보완 후 표적 재확인 — 현재 최종 판정

부모 감사자가 공개 전에 C helper만 수정하고 v2 원문/결과를 보존했다. 새 helper SHA256은 **`78dcb9a4a9409653b9b41397b23424f8c3a76deea5d6dc8f0c7d94f5440cf8f1`**이며 저자 v3의 17조건 결과에 기록된 SHA와 같다. 이 감사에서도 새 v3 정상사본을 다시 별도 `targeted_v3/`로 복제하여 실행했다.

- 정상1조건은 valid=true.
- 앞서 잘못 통과한 **5조건**(빈 전체정정표·정정표 회사승인·운영승인·중복조회4행·bool 종료코드)은 모두 valid=false.
- 연관 **4조건**(필수 정정ID 하나누락·receipt 권한/행동승격·float 종료코드)도 모두 valid=false.
- 기존 낮은 우선순위 N04 관찰1조건은 별도로 재확인했다. 미사용 추가 메타데이터 `1e999`는 여전히 valid=true이나 사용 필드·승인값을 바꾸지는 않는다. 제한된 참조 검사 범위의 비차단 입력 엄격성 관찰로 남긴다.

합계11조건은 **정상1+오류거부9+알려진 비차단 관찰1**이다. 모두 의도한 관찰 결과였으며, 이를 “11개 모든 악성입력 거부”라고 표현하지 않는다. 모델 시행0, 원 v3 정상사본 및 각 검사 입력 불변을 확인했다. 저자17조건·이번11조건은 중복되는 도구 단위 조건이므로 합쳐 독립 모델 성적으로 집계하지 않는다.

따라서 **N01~N03의 공개 전 최소 결함은 해소 확인**이다. 정정표 필수ID는 현재5개를 최소 포함해야 하고 중복을 거부한다. receipt는 정확한4개 도구집합/정수0을 요구하며 거짓 행동·권리/회사승인 선언을 거부한다. scope/output의 live R6/R7·내용·권리·모델행동·회사/운영승인 false 경계는 유지된다.

아직 D helper 게시/새 입력 고정은 하지 않았다. 이번 판정은 위 SHA의 C 코드와 검증 사본에 한정하며 **추후 최종 source freeze/게시도구·D 게시 결과는 별도 검토**가 필요하다. 기존 R6/R7 pin 교체나 후보 기본전환·전체완료의 허가는 아니다. 증거 `06_v3_표적재확인.json`을 참조한다.
