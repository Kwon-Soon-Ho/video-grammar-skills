# R8-4 실행 전 독립 설계 레드팀

최종 판정: **정제된 최종 입력으로 후보 단독·한정 합성 확인을 진행할 수 있다. 실행을 차단할 설계 결함은 발견하지 않았다.** 처음 발견한 과거 평가점수 문단은 모델 실행 전 수행용 사본에서 분리됐고, 원문/변환 지문을 추가 확인했다. 아래 관측 한계와 사소한 형식 모호성은 남는다. 기존 대비 개선량·스킬 독자효과·일반화 성능·새 구조에 대한 미지 시험으로 해석하면 안 된다.

검토 범위는 준비 코드, 실행 전 기대항목/고정기록, 각 candidate의 task.txt와 inputs뿐이다. 과거 사례·과거 수행 결과·운영 D 원문·다른 실행/검토 결과는 열지 않았다. 네트워크, CU, AE, API, 추가 에이전트를 사용하지 않았다. Python/준비 코드/검사기/후보 모델을 실행하지 않았고 입력을 수정하지 않았다. 출력은 이 설계 폴더에만 남긴다. 이 문서는 준비된 후보 스킬을 **실행한 결과가 아니라 검토한 문서**다.

초기 발견 이후 부모의 명시 요청으로 `준비보완이력/02_과거점수문장_분리/변환.json`과 `R4_통합기록_사용안내_원문.md`만 추가 열람했다. 원문은 이 입력의 정제 전 보존 사본이며 과거 모델 수행 결과 파일은 아니다. 부모는 수행자 모델 실행 0회를 재확인했다. 준비 기반검사의 R5 경로 오류 1회는 부모의 준비보완이력 설명이며 모델 실행 실패와 구분한다. 본 검토가 그 실행 로그를 독립 확인한 것은 아니다.

## 실행 전 고정과 독립 관측

- 기대항목 파일 SHA256은 `a253387aa561e02babdb3502bda16b6f8fc611607ec079b716c814f676607226`이며 고정기록 값과 일치한다.
- 고정기록 SHA256: `498505c79f157e67130e659900220d94d947377ee51ac4fcb9f9e1cf285c07e2`.
- 준비 코드 SHA256: `ebeceef74b99a2fbc8678eae8544b1f1b55be9a2c77a583041fb0dae222c526c`.
- 세 task의 현재 SHA는 기대항목과 모두 일치한다. 실제 입력 파일 수는 각각 78/272/79개로 기대항목과 일치한다. 각 사본의 자기 후보 스킬은 3/5/3개 파일이며 고정된 후보 소스 해시와 모두 일치한다. 다른 후보 스킬 본문/평가 파일은 입력에서 발견되지 않았다.
- 기대항목과 고정기록은 모두 `actual_runs_at_freeze=0`을 선언한다. 이 검토에서 발생한 후보 모델 실행은 0이다. **이 숫자만으로 과거에 어떤 실행도 없었다는 사실을 독립 증명하지는 못한다.** 실행 이력/outputs는 허용된 열람 범위 밖이어서 보지 않았다. 실행 담당자는 첫 모델 호출 직전 그 사실과 입력 해시를 별도로 확인해야 한다.
- 전체 입력별 SHA와 task/후보스킬 대조는 동봉 `실행전_해시와조건.json`에 기록한다. 실제 실행 전후 불변 검사는 이 파일과 대조할 수 있다. 이 검토는 candidate의 외부 fixture_before.json을 열지 않았다.

## 발견과 필요한 처리

**F1 — 과거 결과 요약 잔존: 실행 전 해소 확인.** 초기 `case2/inputs/Phase00/07_실행도구/R4_통합기록_사용안내.md:33`에 “과거 11/12·8/8”과 과거 record-steward 구형 fixture의 이관 대기 상태가 있었다. 새 시험 정답이나 15개 기대항목의 복제는 아니지만 과거 결과 미제공 주장에는 반례였다. 부모가 모델 실행 0회 상태에서 해당 문단 한 개를 수행용 사본에서 분리했다. 보존 원문 SHA `77e4147a908d97bc177431c8af64bf7615b106aca72eb71586cff9561bbcda63`, 최종 사본 SHA `bf7afb6631535b5c902a0639a62a290b6237b3712ed7b09a83f2cd8827e56730`가 변환 기록과 모두 일치하며 줄 대조의 차이는 해당 한 문단 제거뿐이다. 최종 case2의 텍스트 재검색에서 두 과거 점수는 더 이상 나오지 않는다. 변환 기록 SHA는 `84d0b28f586c807860b66fa946b1ce8bfdb191f01e1088c74119a542d7b115c1`이다. 기대항목과 고정기록의 SHA는 위 값 그대로이며, 동봉 전체 입력 해시도 최종 정제 사본을 가리킨다. 본 검토는 정제하지 않았다.

고정기록 `performer_sources`는 운영 원문의 지문이므로 이 한 파일의 최종 수행 사본 지문과 다르다. 최종 fixture 지도와 별도 변환 기록을 함께 실행 고정 묶음으로 보존해야 하며, 원문 해시와 사본 해시가 무조건 같다고 설명하면 안 된다. 최종 준비 상태는 준비 코드 단독 출력에 이 기록된 정제 한 건을 적용한 상태다. 외부 원문/고정 pin을 바꿔 통과를 만든 것이 아니다.

**F2 — preflight 정상은 준비 코드에 명확하지만 이 검토에서 재실행하지 않았다.** 준비 코드는 case2의 실제 사본 `자료검증.inspect_file(p)`와 `R5_디자인적용검사.inspect(app,base=db)`가 모두 valid일 때만 준비를 계속하도록 assert한다. 검사기 BASE도 각 사본 루트에 있고 R5에는 base를 명시한다. 실제 R4의 schema_version=0.2.0, record_id=R8-NEW-READ, version=0.1.0, R5의 data_scope=spec_example과 새 연결 ID/판본/SHA가 서로 맞는 것은 읽기·해시로 독립 확인했다. R4 SHA는 `895dd16c3fde41baeb64ecedbe374b757c621dffe7fa4107fa2c70d22c193994`이다. 그러나 준비 후 코드/의존성 실행의 정상까지 본 검토가 관측한 것은 아니다. 실행 담당자의 별도 preflight 기록을 보존해야 하며 본 보고를 실제 재실행 성공으로 인용하면 안 된다.

**F3 — 과거 미사용/신규성의 강한 독립 증명은 없다.** 준비 코드는 새로운 메모·요청을 만들지만 case2 R4/R5 내용은 기존 설명용 예시를 복사해 ID/설명/연결을 바꾸는 구성이다. 따라서 ‘새 요청과 참조 조합을 검토하는 합성 확인’은 맞지만 ‘이전에 보지 못한 전혀 새로운 기록 구조’는 아니다. 과거 원문을 보지 않았으므로 case1/3도 역사 전체와 중복되지 않는다는 것은 고정기록의 선언 이상으로 검증하지 않았다. 이 제한은 현재의 후보 단독 확인 자체를 차단하지 않는다.

## 기대항목의 구체성·공정성

- case1은 허용 필드/대상 판본/보존 필드/backup/diff를 명시하므로 실제 JSON 의미 대조와 byte 검사로 판단 가능하다. 같은 ID의 서로 다른 판본 자체를 중복 오류로 몰면 오판이다. byte backup은 내용 동일성을 확인하되 같은 줄바꿈의 다른 표현만으로 실패 처리하지 말고 실제 byte 동일성을 기준으로 해야 한다. 허용 필드의 표현은 문장 복제가 아니라 원문 지지·설명용 자격·예/반례의 기능으로 의미 채점한다.
- case2는 입력 변경 0과 두 정상 구조 검사 결과를 확인하면 된다. 구형 참고가 valid=false여도 전체 대상 실패로 합치면 안 된다. R4 구조 valid와 unresolved, R5 valid와 human_review_queue를 함께 인정해야 한다. 정상 결과를 얻기 위해 값을 ‘수리’하면 실패다. 지원되지 않는 full R6R7을 필수 실행으로 채점하는 것은 부당하다.
- case3는 D1~D3 유지, D4 한계, D5 대상/판본/범위의 세 축이 서로 독립적으로 드러나야 한다. 모든 항목을 무조건 보류하거나 새 장식/모션을 요구하는 결과는 실패지만 제공하지 않은 실제 가독성/실측을 확인하지 못한 것은 실패가 아니다. 실제 사람이 답했다고 꾸미지 않은 질문 제안은 정당한 산출물이다.
- 15개 기대항목은 각각 여러 조건을 묶고 있다. 독립 채점은 각 문장의 어느 하위 조건이 충족/미충족/미관측인지 증거를 남기고, 전체 실패/성공으로만 압축하지 않는 편이 공정하다. 정확히 특정 보고서 문구·필드명·질문 형식만 맞아야 통과시키면 안 된다. 표본 3개의 집계로 일반 성능/개선율을 만들지 않는다.
- case3 task 첫 문장은 `검토결과.md/검토기록.json`, 공통 말미는 `결과.md/결과.json`을 요구한다. 둘 다 산출 가능한 범위라 차단은 아니지만 내용이 같고 한 쌍만 남긴 경우 핵심 의미 기대항목 실패로 과대 평가하지 않아야 한다. 실행을 시작하기 전에 명명 우선순위를 안내하면 더 명료하다.

## 변경 경계와 관측 조건

case1 허용 쓰기는 `작업초안/연결설명_지식초안.json` 하나와 run 안의 결과/backup이다. 전체 파일은 바뀌므로 비대상 두 records와 document_version/display_name/id/state의 의미 보존을 JSON 대조하고, 나머지 입력은 모두 byte 보존으로 확인한다. backup이 쓰기 전에 존재했는지는 사후 파일 한 개로 증명할 수 없으므로 실행 도구 로그/명령 순서를 함께 보존해야 한다.

case2/3는 inputs 전체 byte 불변이다. Python import 시 `__pycache__` 같은 새 파일을 inputs에 만들면 ‘읽기 전용’ 경계를 흐릴 수 있다. 실행자는 `-B` 또는 `PYTHONDONTWRITEBYTECODE=1`을 사용하고 결과는 outputs에 보존할 수 있다. `자료검증.py --output`은 inputs/08_검증결과를 쓰게 제한되므로 이 시험에서는 `--output` 없이 stdout/API 결과를 outputs에 보존하는 것이 적절하다. 도구 제한을 고치거나 허용 입력 변경을 늘릴 이유는 없다.

해시와 실제 산출물로 입력 변경은 관측 가능하다. 자기기록 transcript만으로 실제 읽기·명령 실행·종료값·backup 선후·네트워크 미사용까지 독립 관측했다고 해서는 안 된다. 실행 담당자의 도구 호출/종료 기록을 함께 남겨라. 그 기록이 없다면 해당 항목은 ‘자기기록, 독립 관측 미확보’로 한정한다.

실행은 기대항목/고정기록이 먼저 확정된 다음에 수행해야 한다. 수정이 필요하면 기존 해시를 조용히 갱신하거나 이미 실행한 결과를 보고 기대항목을 고치지 말고 변경 이유/새 freeze와 실행 전 0회를 다시 명시한다. 같은 사례의 후속 실행은 재시험이며 새 미지 사례로 집계하지 않는다.
