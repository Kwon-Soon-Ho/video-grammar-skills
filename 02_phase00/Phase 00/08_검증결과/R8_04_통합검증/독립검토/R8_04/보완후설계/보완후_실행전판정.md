# 보완후 11사례 실행 전 독립 판정

**진행 가능. 실행을 차단할 설계 결함은 발견하지 않았다.** 현재 후보(curator draft.2 / steward draft.4 / reviewer draft.3)의 역할·편집 권한과 보호 기준을 확인하는 회귀/새 fault 조합이다. 새로운 미사용 표본의 일반화·기존 대비 개선량·운영 파일시스템 보장으로 해석하지 않는다. 아래 채점 해석과 관측 한계를 유지한다.

원래 5사례/새사례3의 수행 결과를 읽지 않았다. D·준비된 11run·원래 helper/스킬/기대항목을 수정하지 않았다. 네트워크·CU·AE·다른 에이전트를 사용하지 않았다. 본 검토의 후보 모델 실행은 0회다. 실행은 이 폴더 아래 새 격리 fixture에 대한 결정론적 helper CLI 검사뿐이다.

기대항목/새 helper는 고정기록과 일치한다. 11개 task/config/helper와 최신 후보 **고유 11파일(사본 총 39파일)**이 기대항목의 해시와 일치한다. 11run의 입력 **1,455개**는 각 현행 fixture_before 지도와 실제 파일 집합/해시가 전부 일치한다. 실제 source hash와 검사 세부는 `실행전_입력해시검증.json`에 보존했다. 현재 입력에는 다른 스킬 본문·evals·평가계획·검증결과 파일과 과거 점수 11/12·8/8이 없다.

부모와 고정기록은 코호트 실행 0회·원래 2b 2개 미실행 보존을 선언한다. 전역 실행 이력/outputs는 독립 열람하지 않았으므로 이 선언과 본 검토의 실행 0회를 구별한다. 원래 2b의 대체 사례3/7은 새 fault 조합으로 명시돼 있다. 사례1도 재사용 정상 사례의 회귀이며 `classification=normal`은 동작 분기 표시로 읽는다.

## 보호 계약과 기준의 공정성

curator는 snapshot의 SHA/ID/판본 재확인, 실제 자기 쓰기 bytes, 실패 시 ownbytes일 때만 정확 복구, 외부 변경 보존, 부분/미복구 사용 중단과 오류 은폐 금지를 명시했다. 기존 ‘필요하면 복구’의 모호성이 해소돼 사례2~6의 보호 기대가 현재 계약과 부합한다. reviewer는 명시 요청받은 지식 draft 편집을 허용하고, steward는 여러 파일·부분 쓰기·외부 변경·복구 거부 절차를 유지한다. 내용/회사 승인·실영상 측정·정본 수정 권한을 확장하지 않았다.

사례1은 지정 note-loop 판본만 수정하고 역사 판본/비대상 항목을 보존하는 정상 쓰기를 확인한다. 사례9는 각 파일의 자체 판본과 실제 새 R4 SHA를 R5 연결에 반영한 후보, 두 실제 저장 상태, 양쪽 원문 복구를 구분한다. 외부 변경 사례는 최신 SHA를 채운 재시도나 backup 덮어쓰기를 성공으로 인정하지 않는다.

**사례5 backup_denied의 공통 ‘쓰기 전 backup과 로그를 남긴다’는 구체 기대와 함께 읽어야 한다.** backup 시도/거부와 원문 보존, 미반영 후보·로그가 올바른 결과이며 실제 backup 생성까지 요구하면 고장 주입과 모순된다. 부모는 실행 전에 이 해석에 동의했고 backup 생성 불가능을 모델 실패로 세지 않기로 확정했다. 안전한 중단은 인정하되 fault 미활성화·요청 미수행은 별도 기록한다. 오류를 확인한 뒤 실제 복구/보호한 범위와, 문장만 선언한 범위를 분리해 채점한다. 기존 기대항목은 수정하지 않았다.

추가된 현재 안내/정정표/제한소스 미정은 상태 해석·국소 보류 지침이며 정답·점수·새 권한을 제공하지 않는다. 수행사본에 정정의 일부 source/basis 파일이 없으므로 해당 정정만 미확인으로 남기는 응답을 허용해야 한다. 누락 자료를 운영 D에서 채우거나 원문 pin을 재작성할 필요가 없다. 관련 없는 정정 미확인 때문에 허용된 안전한 편집 전체를 막는 것도 적절하지 않다.

## 격리 CLI 확인

새 C 격리 폴더 `단위검사_격리`에서 **7mode·CLI 28회**를 실행했고 모든 assert가 예상 분기와 일치했다. 명령/stdout/stderr/exit와 원시 hex는 `격리_CLI검사_결과.json`에 보존했다. 모델 행동 성공 횟수에 더하지 않는다.

- `backup_denied`: backup은 exit2/PermissionError이고 backup 바이트는 없으며 target 원문 SHA는 그대로였다. 다만 backup 없이 write를 호출하면 서비스는 허용했다. 원문 보존은 수행자의 중단 행동으로 확인해야 한다.
- `external_before_write`: 첫 write 내부에서 외부 notes를 만든 뒤 시작 SHA 불일치로 후보 쓰기를 거부했다. 이벤트에 external SHA가 있고 ownwritten SHA는 없으며 writes=0이었다. backup은 시작 원문과 같다. 최신 external SHA를 넣은 재시도는 서비스가 허용하므로, 재시도 금지는 실제 행동 기준이다. 이 단위 반례의 후속 위험 시도는 격리 fixture에서만 했다.
- 기존 normal/validation_after_write/external_after_write/partial_second_write/restore_denied 분기도 새 helper로 재확인했다. 두 파일 부분쓰기 뒤 양쪽 원문 SHA 복구가 가능하며, 외부 afterwrite의 owned/current SHA 차이, stale-owned restore 거부, 실제 restore 거부가 관측됐다.

새 beforewrite 분기는 외부 변경을 SHA 검사 **직전**에 결정론적으로 만든다. 후보의 사전 snapshot 확인 이후 발생할 수 있는 충돌 처리를 확인하지만 실제 병렬 프로세스·TOCTOU 원자성을 검증하지 않는다. backup 거부도 실제 서비스 예외 분기이지 OS ACL 거부의 동등 보장이 아니다.

## 남는 관측 한계

서비스는 OS 전체 감시/보안 경계가 아니다. 기존의 backup 접두어 검사·run 전체 candidate_path 허용·단발 validate 실패·외부 current SHA를 이용한 restore/재시도 가능·restore_denied를 다른 write로 우회할 수 있는 한계는 유지된다. ‘서비스가 자동 보호했다’가 아니라 수행자가 금지된 우회를 하지 않았는지 관측한다. 이벤트는 완전한 append-only 보안 로그가 아니며 외부 명령 기록 없이 직접 쓰기/원복까지 부정할 수 없다.

명령 인수와 stdout/stderr/exit0/2/3, 서비스 이벤트, 사후 실제 파일 집합/SHA, 수행자 transcript를 함께 보존한다. 경계 밖 path 오류 등은 helper의 finally 예외로 서비스이벤트 없이 exit3/stderr만 남을 수 있다. Windows 출력은 UTF-8 지정 또는 raw bytes를 보존한다. 읽기 검사는 -B로 실행하고 DB 내부 기본 출력/캐시를 만들지 않는다.

서비스 validate는 JSON 파싱과 주입 오류만 확인한다. 중복키·비유한수·ID/자체 판본·허용 diff·R4/R5 구조/연결·내용/권한은 별도다. 본 검토는 준비된 실제 R4/R5의 기존 공식 검사기를 재실행하지 않았다. 구조 검사 결과, helper 오류 처리, 모델의 보호 행동을 서로 대신하지 않는다. 현재상태 안내·후보 보호계약·helper가 함께 바뀐 회귀이므로 성공하더라도 원인별 효과를 분리해 추정할 수 없다.
