# R8-3 게시 스크립트 — 제한 정적 검토

2026-10-15. 요청에 따라 `phase00-build/R8_03_결과정리.py`와 import된 `공통지원.py`의 경로/보존·상태 처리 코드를 읽었다. 실행자 출력·채점 결과·미완료 과제·최종판정 파일의 내용은 읽지 않았다. 게시 스크립트는 실행하지 않았다. 이 문서는 최종6회 결과의 독립 감사가 아니다.

검토한 게시 스크립트 SHA256: `07e324f6e48cf5f43832e82eb0e168fa4c21f5219824f34284e19fb350ddda02`.

## 결론

보고문구의 범위 구분은 적절하다. 다만 **원문 보존 복사의 양쪽 IO/해시 대조**와 **후속 검사 실패 시 상태**를 보완한 뒤 게시 실행하는 것을 권고한다. 아래는 코드만으로 확인한 사항이며 실제 오류가 발생했다고 주장하지 않는다.

## 보완사항

### P-01 · 최종 검사 전에 완료 상태를 저장

위치: 게시 스크립트83~103행.

83행의 결과안내와 86~94행의 진행상태/안내는 개발 비교·레드팀 완료 및 출력 피드백 대기로 저장된다. 이후96~102행에서 착수174개 변경집합·backup·검토입력의 변경 허용집합·R6/R7 현재 조회·링크를 검사한다. 이 후속 검사 중 하나가 실패하면 최종 보존확인JSON은 없지만 완료처럼 보이는 상태/안내는 이미 남는다. 예외 처리나 게시 실패 상태 분기가 없다.

권고: 완료형 상태·완료 안내 반영은 최종 검사가 성공한 뒤로 미루거나 게시중/실패/부분반영을 실제 상태에 맞게 명시한다. 검사가 생성된 문서를 대상으로 해야 하면 임시 작성/게시중 상태를 먼저 쓰고, 성공 후 마지막에 완료 상태를 반영하는 순서로 분리할 수 있다. 실패 때 실제 반영 범위를 숨기지 않는다. 모든 파일 묶음의 원자적 게시를 새로 구현하라는 요구는 아니다.

### P-02 · 긴 경로 처리가 복사 원본에 적용되지 않음

위치: 게시 스크립트7·17~24행, `공통지원.py:5`.

`exact`는 목적지에만 `io(dst)`를 적용한다. 기존 목적지 검사에서 `sha(src)`, 새 복사에서 `shutil.copy2(src,q)`는 원본의 일반 Path를 그대로 쓴다. 공통 `sha`도 그대로 `read_bytes()`를 호출한다. 원본 열거 역시 일반 `source.rglob`이다. 따라서 ‘모든 IO에 긴경로를 일관 적용했다’는 설명은 현재 코드와 다르다. Python/Windows 설정에 따라 일반 긴 경로가 작동할 수 있지만, 그 환경 의존을 여기서 검증하지 않았다.

권고: archive에 사용할 원본/목적지 접근 경로를 같은 방식으로 정규화하고 source 읽기/hash/copy·필요한 디렉터리 열거에 일관 적용한다. 표시용/상대경로 계산은 별도로 유지해 `\\?\` 접두어 유무로 `relative_to`가 깨지지 않도록 한다. IO 정규화 자체를 source 파일 변경으로 해석하지 않는다.

### P-03 · 새 복사 후 바이트 동일성 확인 부족

위치: 게시 스크립트17~21행.

목적지가 이미 있을 때는 원본과 hash를 비교하지만 새 파일은 copy2 후 목적지 hash만 `archived`에 기록한다. 그 값이 복사 전 검토된 원본 바이트와 같다는 assert가 없으며 원본이 복사 중 달라졌는지도 대조하지 않는다. 시작의 C_result_hashes 확인은 게시 시작 전 검토입력 대조로 유효하지만, 뒤의 모든 실제 보존 복사가 그 바이트와 일치하는 확인을 대신하지 않는다.

권고: 복사 전 원본 hash와 복사 후 원본/목적지 hash를 대조해 일치해야 archived에 기록한다. 가능하면 최종 감사에서 고정된 원본 hash와도 연결한다. 불일치는 보존 실패/재검토로 남기고 기존 목적지를 덮어써 숨기지 않는다. 전후 대조만으로 원자 잠금·일시 변경 부재까지 보장한다고 설명하지 않는다.

## 유지할 코드·보고 경계

- 시작에 독립 최종판정의 한정 완료/차단 없음 및 D/C 검토입력 hash 일치를 요구한다. 따라서 현재 미완료 상태에서 이 게시 스크립트를 실행해도 된다는 결론이 아니다.
- 착수174개 중 사전 변경4개, 게시 후 R8-4 계획1개를 추가한5개만 허용한다는 집합 검사는 다른169개 보존의 경계를 명시한다. D_source_hashes에서 게시 후 변경 가능한 범위도 edited 집합으로 제한한다.
- `safe`는 resolve 뒤 지정된 Phase00 하위인지 확인한다. archive 기존 파일의 다른 바이트를 자동 덮어쓰지 않고 중단하는 처리도 유지 가치가 있다.
- 결과 안내42·75~79행과 최종JSON은 R8-3 출력 피드백 대기, 후보 미채택/기본 미전환, R8·Phase00 미완료,01-A 미시작을 분리한다. 별도 D R6/R7 현재 조회를 수행 사본의 full 통과로 옮기지 않는 문구도 정확하다.
- 각1회·총6회라는 보고는 최종6회 완료/판정/해시 근거가 실제로 마련된 후에만 사용한다. 현재 결과의 성공 여부는 이 정적 감사에서 확인하지 않았다.
- R3 제공 자료는 이식 검토 기록5절 발췌이고 원격 원문/학술 전문/외부 코드 최신 재검증은 없다고 밝힌다. 원문 보관 상태와 정적 뷰어의 HTML/데이터 검사·브라우저 시각검수 미실시도 분리한다.
- 기존 R8-1/2 유지 회신이 R8-3 출력/전체 완료 회신이 아니라는 문구를 유지한다. 실제 질문/답변의 정확성은 요청 범위상 이번에 재감사하지 않았다.

이 검토는 여기서 종료한다. 게시 스크립트 보완 확인과 최종6회/공식 뷰어/실제 출력·채점의 독립 감사는 별도 요청의 범위다.
