# 수집 스킬 수정 결과와 현재 위치

## 요청과 적용 방식

기존 분석 스킬의 이름과 UI 호출 정책을 유지하며 Anthropic skill creator 방식으로 수정 후보 draft.10을 만들었다. 기존 draft.9 전체 19개 파일은 로컬에서 해시 백업했다. 중요한 분기점도 Markdown으로 기록하며 PDF는 만들지 않았다.

이번 작업에는 실제 요청→판본별 실행→별도 AI 내용 검토→사용자 결과 검토라는 루프가 적합하다. 이는 설치된 두 creator 지침을 읽고 선택한 작업 방식이다. 두 creator 자체의 성능 우열을 실험으로 입증한 것은 아니다.

## 바뀐 동작

- 기본 수집을 Markdown으로 하고 JSON 검사는 요청/기계 연계가 필요한 선택 경로로 둔다.
- 원본 관측·계산·기능 해석·변경안·새 제안의 층을 구별한다.
- 전체 배치·위계·재질·배경/전경·부품 역할/조합을 먼저 기록하고 수치는 필요에 따라 보강한다.
- 전체 사례와 레이아웃/흐름/독립 동작을 연결하고 반복은 번호/판본·현재 근거·차이·미검증으로 기록한다.
- 원본 언어는 충실히 수집하되 이후 다른 스타일의 활용도 허용한다.
- 새 브리프·화면·렌더를 수집 종료 조건으로 두지 않는다. 미관측 동작은 미상으로 남긴다.
- JSON0.4는 유지하고 새 현행 판본을 draft.10으로 구분한다. 과거 기록을 새 성능 통과로 바꾸지 않는다.

## 실제로 실행한 비교

동일한 두 과제를 구버전과 수정판에 각각 맡겼다. 실행 에이전트는 새 문맥으로 원본 표본과 해당 스킬만 받았으며, 정답/기존 분석/수정 이유를 주지 않았다. 이후 별도 새 문맥 AI가 원본과 각 결과를 대조했다. 버전 라벨은 보이므로 블라인드 비교는 아니다.

1. S/W 장의 192/204/216초 원본 표본으로 새 수집 기록.
2. 프로젝트 지원 134/172초 원본으로 전체 사례와 반복 부품/차이 연결.

네 실행 모두 기본 6개 기준을 충족했다. 이것은 결과가 무오류이거나 수정판이 더 우수하다는 뜻이 아니다. 구버전의 문구 오독과 수정판의 구름 아이콘 오독이 발견됐다. 수정판은 일부 부품의 직접 조회가 더 명시적이고 구버전은 일부 공간/occurrence 연결이 더 상세했다. 이 두 과제만으로 전반적 정확도 향상·실제 재사용 성공·회사 승인을 주장하지 않는다.

## 확인과 한계

JSON 판본 경계/역사 자료 읽기, renderer, 잘못된 해시 거절, 내부 링크와 UI 호출 정책 보존을 확인했다. 최초에는 PyYAML 설치가 막혔으나 승인 경로 복구 후 작업 폴더에만 PyYAML 6.0.3을 설치했다. Anthropic quick_validate.py를 로컬 후보와 D: 활성 스킬에 실제 실행하여 모두 통과했다. 형식/코드 호환 검사와 내용 정확도/수집 품질은 별도다.

원본 연속 재생·음성·정본 DB 입력·전체 프레임 검수는 이번 시험에 없다. 토큰/속도·비용 개선도 계산하지 않았다.

## 다음 큰 작업 선택

1. 사용자 결과 검토와 오독 검수 보강(추천): 두 과제의 실제 수집 기록을 보고 기록 밀도·부품 단위·발견 오독을 피드백한다. 중요한 식별/근거 대응을 평가에서 더 잘 잡도록 보정하며 전편 확장은 유보한다.
2. 수정판으로 다른 구간 수집: S/W·경영지원의 새 표본에 적용해 같은 기록 방식이 유지되는지 확인한다. 전편 완료가 아니라 추가 개발 시험으로 기록한다.
3. 기존 두 사례의 남은 모션 수집: 계약/지원의 도입·구성 차트·사진 비교·마무리 조립을 보강한다. 새 스타일·영상 제작은 하지 않는다.
4. DB 입력 연결 정리: Markdown의 사례/부품/관계/근거를 기존 DB 개념에 대응하고 필요한 구조화 범위를 정한다. 자동 의미 검색이나 정본 등록이 구현됐다고 주장하지 않는다.

## 실제 반영 상태
